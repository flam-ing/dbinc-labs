# 위험한 곳

[← 목차](README.md)

심각한 순서로 적었어요. 줄 번호는 `src/com/nuri/room/` 기준이에요. "실행 확인"이라고 적은 것 말고는 코드를 읽고 판단한 내용이에요(이 지식베이스를 만들면서 프로그램은 돌리지 않았어요).

## 1. 예약번호가 매일 다시 매겨져요

- 번호는 성공한 RSV에서만 `iSeq++`로 올라가요(`RsvManager.java:146-147`).
- 예약을 저장하지 않고 매일 밤 그달 파일 전체를 처음부터 다시 처리해요(`wiki/batch-ops-memo.md:16`).
- 그래서 **앞쪽 RSV 하나라도 성공/실패가 뒤집히면 그 뒤 번호가 모두 밀려요.** 파일에 이미 쌓인 `CXL,…,R0012`는 어제의 R0012가 아니라 오늘의 R0012를 취소해요. 다른 사람의 예약이 취소되거나 바뀌어요.
- 검사 규칙을 바꾸는 수정은 모두 여기에 걸려요. ROOM-23을 미뤄 둔 이유도 이거예요(`issues/ROOM-23.md:32`).
- **고칠 때**: 고치기 전과 후의 출력을 `data/` 네 파일로 비교해서 예약번호가 그대로인지 봐요(`CLAUDE.md` "동작 확인"). 규칙이 바뀌는 수정이면 총무팀과 날을 잡고, 월초(새 파일이 시작될 때)에 넣어요.

## 2. 쉼표만 있는 줄 하나로 그날 배치 전체가 멈춰요

- `split(",")`과 `arr[0]` 읽기가 `try` 밖에 있어요(`RsvManager.java:45-46`). `main`은 `IOException`만 잡아요(`RoomBatch.java:51`).
- `,` 한 줄은 `split` 결과가 길이 0이라 `ArrayIndexOutOfBoundsException`이 `main` 밖으로 나가요. 그 뒤 줄도, 예약표도 찍히지 않아요. 총무팀 공유 폴더 파일이 반쪽이 돼요.
- 종료 코드는 1이에요. "인자 없음"과 같은 값이라 스케줄러에서 원인을 구분하기 어려워요.
- 인수인계 보고서에서 실행 확인했어요(`인수인계-보고서.md:108-114`). 출력과 예약번호를 바꾸지 않고 고칠 수 있는 첫 후보예요(같은 문서 :238).

## 3. `TimeZone.setDefault(Asia/Seoul)` 줄을 지우면 안 돼요

- `RoomBatch.java:21-22`. 주석도 "지우지 마시오!!!"예요.
- 2011-03에 배치 서버를 바꿨는데 새 장비의 시간대가 미국 서부였어요. 미국 서머타임이 시작된 주에 하루가 23시간이 되면서 `dayDiff`(`RsvUtil.java:59`, 밀리초를 하루로 나눠 버림)가 하루 적게 나왔고, 15일 뒤 예약이 "2주 이내"로 통과했어요.
- 인프라팀은 서버 시간대를 바꿀 수 없다고 했어요. 이 줄이 유일한 방어선이에요.
- 출처: `wiki/batch-ops-memo.md:26-28`.

## 4. 500건 한도

- 예약은 `arrRsv[500][10]`(`RsvManager.java:19`)에 담고, 취소된 칸도 다시 쓰지 않아요. 한 달 파일에서 성공한 RSV가 500건을 넘으면 501번째부터 예외가 나서 "형식 오류"가 돼요.
- `iSeq++`(:146)가 배열에 넣기(:148)보다 먼저라서, 실패한 줄도 번호를 하나 먹어요.
- 2010-12 말에 실제로 터졌어요. 그 뒤로 봇이 달마다 새 파일을 써서 피하고 있어요(`wiki/batch-ops-memo.md:24`). 파일을 달마다 나누는 것 자체가 이 한도 때문이에요.

## 5. 시각을 문자열로 비교해요 (ROOM-23, 열림)

- `날짜+시각`을 이어 붙인 문자열로 크기를 비교해요. 옛 봇(2009년판)은 `0930`을 `930`으로 보내요(`wiki/batch-ops-memo.md:32`). `"930"`은 글자로 비교하면 `"1030"`보다 커요.
- 세 자리 시각이 들어오면 빠져나가는 검사:

| 검사 | 코드 | 결과 | 이슈에 적혀 있나 |
| --- | --- | --- | --- |
| 겹침 | `RsvManager.java:135-139` / `:271-275` | 09:00~10:30 예약이 있어도 `930~1000`이 들어가요 | 있음(`issues/ROOM-23.md:18`) |
| 출력 | `RsvUtil.java:77` | `93:0`, `90:0`으로 찍혀요 | 있음 |
| 정렬 | `RsvPrinter.java:60-62` | 10시 예약보다 뒤에 찍혀요 | 없음 |
| R01 청소 | `RsvManager.java:127` | `"930".compareTo("1300") > 0`이라 검사를 건너뛰어요. `대회의실,…,930,1230`(3시간)이 청소 시간에 들어가요 | 없음 |
| 지난 시간 | `:112` / `:257` | 요청과 같은 날이면 `"20100312900"`이 `"201003121000"`보다 커서, 이미 지난 09:00도 통과해요 | 없음 |

- 30분 단위, 운영 시간, 3시간 검사는 `Integer.parseInt`로 숫자 비교라 괜찮아요.
- 옛 봇은 2013-05에도 총무팀 PC에 있었고 그해 두 번 일어났어요(`issues/ROOM-23.md:36`).
- **지금 고치지 마세요.** 숫자 비교로 바꾸면 과거 결과가 뒤집혀 1번 문제가 생겨요. 총무팀과 날을 잡기로 했어요(`issues/ROOM-23.md:32`). `fmtTime`에서 0만 채우는 것(`93:0` → `09:30`)은 판정은 그대로지만 총무팀 공지 문구가 바뀌니 확인 받고 하세요.

## 6. 새 임원을 못 알아봐요 (ROOM-31, 진행 중·높음)

- 검사는 `strEmpNo.startsWith("9")`를 직접 봐요(`RsvManager.java:107`, `:252`). 2012년부터 임원도 사번을 안 바꿔서 새 임원은 3시간 제한에 걸려요(`issues/ROOM-31.md:24`).
- `RsvUtil.isExec`(`RsvUtil.java:118-121`)에 `10001`을 넣었지만 아무 데서도 부르지 않아 효과가 없었어요(`issues/ROOM-31.md:36`).
- **`isExec`를 검사에 연결하지 마세요.** `10001`이 임원이 돼서 총무팀이 넣은 3시간 넘는 RSV가 성공으로 뒤집히고, 1번 문제가 생겨요. 인사팀 임원 명단이 있어야 제대로 고칠 수 있어요.
- 코드를 읽다가 찾은 것(문서에 없음): CHG의 3시간 검사는 **변경을 요청한 사람**의 사번(`arr[2]`)을 봐요(:205, :252). 그래서 총무팀(10001)이 임원의 4시간 예약을 다른 날로 옮기려 하면 "3시간 초과"가 나요.

## 8. 원인이 안 보이는 실패

- `process`가 모든 예외를 "형식 오류" 하나로 바꿔요(`RsvManager.java:59-61`, 스택 트레이스는 주석). 칸 부족, `10:00` 같은 형식, 짧은 요청시각, 500건 초과가 모두 같은 메시지예요.
- 인원 파싱 실패는 조용히 0명(`:82-84`).
- `dayDiff`는 파싱에 실패하면 0을 돌려줘요(`RsvUtil.java:60-62`). 요청시각 앞 8자리가 날짜가 아니면 14일 검사를 그냥 통과해요.

## 9. 입력 처리의 함정

봇 안내문으로 막고 있어요(`wiki/batch-ops-memo.md:36-38`). 배치는 그대로예요.

- 제목에 쉼표가 있으면 뒤가 잘려요(`split(",")`, `RsvManager.java:45`).
- 제목을 비우면 Java `split`이 끝의 빈 칸을 버려서 9칸이 되고, `arr[9]`(:85)에서 예외가 나서 "형식 오류"예요.
- 회의실 이름은 정확히 같아야 해요(`RsvUtil.java:28`). `중회의실 A`(공백), `r01`(소문자), `9층 라운지`는 "없는 회의실"이에요.
- `chkRoom`은 이름을 번호로 바꾸면서 입력 배열 `arr[4]`를 직접 고쳐요(`RsvUtil.java:29`). `doReserve`는 그 뒤에 `arr[4]`를 다시 읽어서(:77) 번호를 얻어요. 순서를 바꾸면 깨져요.

## 10. 그 밖

- **소스에 접속 정보가 있어요.** 주석 처리된 JDBC 연결(`RsvManager.java:29-32`)과 `sendSms`(`:317-322`)에 내부 주소, 계정, 키가 그대로 적혀 있어요. 값이 `DUMMY-`로 시작해 가짜로 보이지만 확인은 안 했어요. 저장소를 밖으로 공유하기 전에 확인하세요.
- 주석 처리된 `insertRsv`(`RsvManager.java:34-41`)는 옛 9칸 배치를 따라요. DB를 다시 켜면 제목 자리에 인원이 들어가요.
- 상태가 모두 `public static`이고 초기화 코드가 없어요(`RsvManager.java:19-26`). 한 JVM에서 두 번 돌리면 결과가 섞여요.
- 쓰지 않는 코드: `Const`의 모든 값, `RsvUtil.isExec`, `RsvUtil.getNow`, `RoomInfo.getFloor`, `vHist`, `ST_DEL`, `sendSms`. `Const` 값을 "고치면 된다"고 착각하기 쉬워요. 코드는 숫자를 직접 써요.
- 화면 출력은 플랫폼 기본 인코딩을 따라요(Windows에서는 MS949). `rpad`는 글자 수로 맞춰서 한글 칸이 어긋나요(보기 문제).
