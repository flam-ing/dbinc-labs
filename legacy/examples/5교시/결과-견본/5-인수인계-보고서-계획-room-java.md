Claude가 세운 계획(원문 그대로예요):

````markdown
# RoomBatch 인수인계 보고서 작성 계획

## Context
RoomBatch(2010년 회의실 예약 배치)를 넘겨받는 사람이 첫날 읽을 보고서를 하나 만들어요. 코드, README, 위키, 이슈를 나눠 읽었어요(코드 6파일, 문서 5개, 이슈 5건, data 4개). 그런데 규칙이 문서마다 다르고, 일부러 남겨 둔 버그가 섞여 있어요. 그래서 보고서는 "무엇이 진짜 규칙인지", "무엇을 건드리면 안 되는지"를 근거와 함께 보여 줘야 해요.
이번 단계에서는 보고서 파일만 새로 만들어요. 코드는 고치지 않아요. 고칠 후보는 6교시에 따로 다뤄요.

## 산출물
- `docs/handover.md` 한 파일(새로 만듦). 근거는 모두 `파일:줄`로 달아요.
- 손으로 따라간 결과는 실제로 돌려서 숫자를 확인한 뒤에 적어요(아래 검증 1).

## 보고서 목차와 담을 내용

### 1. 시스템 한 장 요약
- 흐름: 사원 → 봇 → `D:\room\req\yyyyMM.txt`에 한 줄씩 추가 → 매일 23:00 작업 스케줄러가 그달 파일 전체를 다시 처리 → stdout을 `room_yyyyMMdd.txt`로 총무팀 공유 폴더에 저장 → 아침에 공지(batch-ops-memo §1).
- 코드: `RoomBatch.main` → `RsvManager.process`(RSV/CXL/CHG/QRY) → `RsvPrinter.printAll`. 상태는 모두 static 전역이에요(`arrRsv[500][10]`, `iSeq` 등).
- `arrRsv` 칸 배치표. 머리 주석(RsvManager.java:11-13)은 9칸이라고 써서 틀렸어요. 실제로는 [7] 인원, [8] 제목, [9] 상태예요.
- 현재 규칙 표: 3시간, 청소 12–13시, 09–18시(R05는 07시), 14일, 정원+2, 사번 9로 시작하면 임원, 본인 또는 10001.
- doReserve와 doChange 검사 순서를 나란히 놓은 표. 차이(청소, 정원, 회의실 고정)는 일부러 둔 것이라고 표시해요.
- 빌드·실행 방법, 종료 코드(1, 2), 운영 환경(Windows, JDK 6, DB 대신 파일, ojdbc·conf는 저장소에 없음).

### 2. 위험한 곳 (심각한 것부터)
1. **예약번호를 매번 다시 매기는 것**: 앞쪽 RSV 하나의 결과가 바뀌면 그 뒤 번호가 모두 밀리고, 이미 쌓인 CXL/CHG가 다른 예약을 가리켜요. 모든 규칙 변경에 걸리는 제약이에요.
2. **배치 전체가 죽는 경로**: 쉼표만 있는 줄(`,`)은 `split` 결과가 길이 0이 돼요. 그런데 `arr[0]`을 try 밖(RsvManager.java:45-46)에서 읽고, main은 IOException만 잡아요. 그러면 그날 예약표가 아예 안 나와요(새로 찾은 것, 실행해서 확인할 예정).
3. **TimeZone 줄**(RoomBatch.java:22): 지우면 2011-03 장애가 다시 나요.
4. **500건 한도**: 501번째에서 AIOOBE가 나고 "형식 오류"로 떨어져요. 그 전에 `iSeq++`가 먼저 돌아서 번호도 하나 빠져요.
5. **문자열 시각 비교**(ROOM-23): 겹침, 지난 시간, 청소 검사, 정렬 모두에 걸려요. 세 자리 시각이면 청소 검사도 빠져나가요(이슈에는 안 적힌 부분).
6. **예외를 삼키는 곳**: 모든 오류가 "형식 오류" 하나로 나와요. `dayDiff`는 파싱에 실패하면 0을 돌려줘서 검사를 통과해요.
7. **`chkRoom`이 입력 배열을 직접 고쳐요**. 그리고 `split(",")`의 세 가지 함정(쉼표가 든 제목, 빈 제목, 공백이 든 회의실 이름)이 있어요.
8. **보안**: `sendSms`와 주석 처리된 JDBC 블록에 URL과 키가 하드코딩돼 있어요. 보고서에는 값을 옮기지 않고 위치만 적어요.
9. 기타: stdout 인코딩이 플랫폼 기본값을 따라요. static 상태를 초기화하는 곳이 없어요.

### 3. 코드와 문서가 어긋난 곳
표 하나로 정리해요. 열은 규칙 / README / PRD 2010-01 / booking-rules 본문 / 최신 근거 / Const / 코드예요.
- 최대 시간, 청소 시간, 운영 시간, 예약 기한, 정원, 취소 권한, 임원 판별
- DB 저장과 파일 방식, `today.txt`와 월 파일, SMS, R06 폐지(코드 주석에만 있음), README 빌드 명령에 `-encoding`이 빠진 것
- Const 값은 쓰이지 않아요(MAX_MIN=120, MAX_DAY=7). `isExec`, `getNow`, `getFloor`, `vHist`, `ST_DEL`, `sendSms`도 죽은 코드예요.
- 어떤 문서가 무엇을 덮어쓰는지 우선순위를 적어요(PRD §8, cleaning-contract :13, booking-rules 댓글 :57).

### 4. 위키·이슈에만 있는 이유
이슈마다 상태 / 결정 / 담당·날짜 / 고치기 위한 전제 조건을 적어요.
- ROOM-12 보류: 임원 점심 회의를 변경으로 넣어요. 전제는 "강제 예약" 기능이에요.
- ROOM-19 해결 안 함: 인원은 참고용이에요. 새 봇에서 막았어요.
- ROOM-23 열림: 총무팀과 날을 잡아야 해요. 옛 봇은 2013년에도 아직 남아 있어요.
- ROOM-31 진행 중(높음): 인사팀 임원 명단이 필요해요. `isExec`에 10001을 넣은 시도는 효과가 없었어요.
- ROOM-35 의도된 동작: 2010-02에 회의실마다 의자를 2개씩 더 놓았어요.
- 운영 메모: 2011-03 TimeZone 장애, 2010-12 500건 초과, 2010-07 DB 계정 차단, 2010-12 SMS 계약 종료.
- 계약: 청소 중 회의는 업체 "미이행"으로 처리돼 대금에서 빠져요. 그래서 청소 시간을 막아요. R05가 07시에 여는 건 LA 사무소와의 정기 회의 때문이에요.
- 지키지 않은 약속: booking-rules 본문은 "곧 고칠게요"라고 해 놓고 안 고쳤어요. ROOM-35를 운영 메모에 적겠다는 것도 안 했어요.

### 5. 6교시에 고칠 후보
안전한 순서로 적고, 후보마다 "출력이 바뀌는가"와 "예약번호에 영향이 있는가"를 표시해요.

| 순위 | 후보 | 파일 | 출력 변화 | 번호 영향 |
| --- | --- | --- | --- | --- |
| 1 | 쉼표만 있는 줄에서 배치가 죽는 문제: `split`과 `arr[0]`을 try 안으로 옮겨 "형식 오류"로 처리 | RsvManager.java:45-47 | 기존 data 4개는 diff 없음 | 없음(지금은 그 줄에서 전체가 멈춤) |
| 2 | `arrRsv` 머리 주석을 실제 칸에 맞추기 | RsvManager.java:11-13 | 없음 | 없음 |
| 3 | Const 값 맞추기(180, 14) 또는 "안 씀" 주석 달기 | Const.java | 없음 | 없음 |
| 4 | README를 현재 규칙과 `-encoding UTF-8`에 맞추기 | README.md | 해당 없음 | 없음 |
| 5 | 501번째에서 번호가 빠지는 것: 칸 검사를 `iSeq++`보다 앞에 두기 | RsvManager.java:146 | 500건 넘을 때만 | 넘은 뒤에는 모두 실패라 사실상 없음 |

**고치지 말 것**(보고서에 명시): doChange에 청소 검사 추가(ROOM-12), 정원 +2(ROOM-35), ROOM-23 숫자 비교, ROOM-31 `isExec` 연결, ROOM-19, TimeZone 줄 삭제.
**논의 후 결정**: `fmtTime`에서 세 자리 시각 앞에 0 채우기(`93:0`→`09:30`). 출력만 바뀌지만 ROOM-23과 닿아 있어서 총무팀 확인이 필요해요.

## 검증 (보고서를 쓰기 전과 쓴 뒤)
1. `javac -encoding UTF-8 -d classes src/com/nuri/room/*.java`로 빌드해요. 그다음 `data/` 4개를 각각 `actual/*.txt`에 저장해요. 손으로 따라간 숫자와 실제 출력을 맞춰 봐요(commands 19/19, old-bot 6/1, month, empty "예약 없음"). 다르면 보고서에는 실제 출력을 적어요.
2. 쉼표만 있는 줄이 정말 배치를 죽이는지 임시 파일(`actual/comma.txt`, gitignore 대상)로 재현해서 확인해요.
3. 보고서의 `파일:줄` 근거를 몇 개 골라 다시 열어 봐요.
4. `git status`로 새로 생긴 파일이 `docs/handover.md` 하나뿐인지 확인해요(`actual/`, `classes/`는 gitignore 대상).
````
