# 실습 1 견본: 열고, 묻고, 돌려 보기 (room-java)

강사가 회의실 예약(room-java)으로 실제로 돌린 결과예요. 권한 승인이 없는 방식(헤드리스)으로 돌려서, 화면에서 승인 카드가 뜨는 자리는 "승인이 필요해서 멈췄다"는 말로 나와요.

## 첫 질문 (Manual, 1분 28초)

보낸 말:

```text
이 폴더가 어떤 시스템인지 파악해서 알려 줘. 무엇을 하는 프로그램이고, 입력과 출력은 무엇이고, 문서와 코드가 다른 곳이 있는지 봐 줘. 아직 아무것도 고치지 마.
```

원본 실행은 승인이 없어서 하지 않았어요.

Claude가 한 말(원문 그대로예요):

````markdown
요청하신 대로 아무것도 고치지 않았습니다. 샘플 데이터를 실제로 실행해 보려고 빌드 명령을 시도했지만 승인이 필요해서 멈췄습니다. 그래서 아래의 동작 설명은 코드를 읽고 데이터를 손으로 따라가서 정리한 것입니다.

## 어떤 시스템인가

사내 **회의실 예약을 밤마다 한 번에 처리하는 Java 프로그램**입니다(2010년, JDK 6 시절 코드, 약 680줄). README에 교육용 가상 자료라고 적혀 있습니다.

- 메신저 봇이 직원 요청을 텍스트 파일에 한 줄씩 쌓습니다.
- 매일 밤 11시에 `RoomBatch`가 그달 파일을 **처음부터 다시** 읽어 규칙을 검사하고 예약표를 새로 만듭니다.
- 예약을 따로 저장하지 않습니다. 모두 메모리 안에서만 처리합니다(`RsvManager.arrRsv`, 최대 500건). 그래서 예약번호 R0001…도 매번 처음부터 다시 매겨집니다.

| 파일 | 역할 |
|---|---|
| `RoomBatch.java` | 진입점. 시간대를 서울로 고정하고 파일을 읽은 뒤 결과를 출력 |
| `RsvManager.java` | RSV(예약)/CXL(취소)/CHG(변경)/QRY(조회) 처리와 검사 규칙 |
| `RsvUtil.java` | 날짜·시각 계산, 회의실 이름→번호 변환 |
| `RsvPrinter.java` | 예약표 정렬과 출력 |
| `RoomInfo.java` | 회의실 목록(코드에 직접 박혀 있음) |
| `Const.java` | 상수. 실제로는 거의 쓰이지 않음 |

## 입력과 출력

**입력**: 인자로 받는 UTF-8 텍스트 파일 하나입니다. 칸은 쉼표로 나누고, `#`로 시작하는 줄과 빈 줄은 건너뜁니다.
```
RSV,요청시각,사번,이름,회의실,날짜,시작,종료,인원,제목
CXL,요청시각,사번,예약번호
CHG,요청시각,사번,예약번호,날짜,시작,종료
QRY,요청시각,날짜
```

**출력**: 모두 표준 출력으로 나갑니다.
1. 요청 줄마다 `[0012] RSV OK ...` 또는 `[0012] RSV ERR 이유` 한 줄
2. 날짜별 예약표(회의실, 시각, 예약번호, 이름, 인원, 제목)
3. 마지막 줄에 성공/실패 건수

종료 코드는 인자가 없으면 1, 파일을 열 수 없으면 2입니다. `room_yyyyMMdd.txt` 파일은 스케줄러가 표준 출력을 파일로 돌려서 만듭니다. 프로그램이 직접 쓰지 않습니다.

## 문서와 코드가 다른 곳

### 1. 규칙 값이 다름 (코드가 나중 결정을 따르고, 문서가 낡은 경우가 대부분)

| 항목 | README / 기획서 / 규정 본문 | 코드 | 비고 |
|---|---|---|---|
| 최대 예약 시간 | 2시간 | **3시간** (`RsvManager.java:107`, `:252`에 180 직접 입력) | 규정 댓글(2010-05)에서 3시간으로 바뀜. `Const.MAX_MIN=120`은 쓰이지 않음 |
| 대회의실 청소 시간 | 12:30~13:30 | **12:00~13:00** (`RsvManager.java:127`) | 시설관리 문서(2010-11) 기준이 코드와 같음 |
| 운영 시작 | 모든 방 9시 | **화상회의실(R05)은 7시** (`:101`) | 시설관리 문서 4절. `Const.OPEN_TIME`은 쓰이지 않음 |
| 회의실 목록 | R01~R06 | **R06(9층 라운지) 주석 처리됨** (`RoomInfo.java:17`) | R06을 없앤 이유를 적은 문서가 없음. 규정·기획서에는 R06이 그대로 있음 |
| 정원 | 기획서: "정원을 넘으면 안 돼요" | **정원+2까지 허용** (`:122`) | 규정 4절과 ROOM-35에서 의도된 동작으로 확인됨. 기획서만 낡음 |
| 며칠 앞까지 | 2주 | 14일 (`:117`) | 일치. 다만 `Const.MAX_DAY = 7`이 남아 있어 헷갈림 |

### 2. 저장 방식과 실행 환경
- 기획서 5·6절과 README는 그룹웨어 DB(`TB_ROOM_RSV`), `lib/ojdbc14.jar`, `conf/db.properties`를 쓴다고 합니다. 실제 코드는 **DB를 전혀 쓰지 않고**, DB 코드는 주석으로만 남아 있습니다(`RsvManager.java:28-42`). `conf/`와 `lib/` 폴더도 없습니다. 운영 메모 2절만 실제와 맞습니다.
- 입력 파일 이름: README와 기획서는 `today.txt`(그날 요청)이고, 운영 메모는 `yyyyMM.txt`(그달 누적)입니다. 매일 처음부터 다시 처리하는 지금 구조에는 운영 메모 쪽이 맞습니다.
- 예약 확인 문자는 기획서에 기능으로 있지만, 코드에서는 호출이 주석 처리되어 있습니다(`:159`). 2010-12에 껐다고 메모에 기록되어 있습니다.

### 3. 임원 판정 (ROOM-31, 진행 중)
- 사번 체계 문서는 "첫 자리 9 = 임원"이라고 합니다. 그런데 인사팀 댓글에 따르면 2012년부터 임원도 사번을 바꾸지 않습니다. 즉 문서 자체가 낡았습니다.
- `RsvUtil.isExec`에 총무팀 사번 10001이 추가되어 있지만, 이 메서드는 **어디서도 호출되지 않습니다**. 실제 검사는 `startsWith("9")`를 그 자리에서 직접 봅니다(`:107`, `:252`).

### 4. 변경(CHG)과 예약(RSV)의 검사가 다름
- 기획서는 "변경도 같은 검사를 한다"고 하지만, CHG에는 **청소 시간 검사가 없습니다**. ROOM-12에 기록되어 있고, 임원 점심 회의 때문에 일부러 고치지 않고 보류한 상태입니다.
- 같은 검사 코드가 두 곳에 복사되어 있어서, 한쪽만 고치면 이런 차이가 또 생길 수 있습니다.

### 5. 문서에 없거나 문서와 다른 세부 동작
- **옛 봇의 세 자리 시각(`900`)** (ROOM-23, 열림): 시각을 글자로 비교해서 겹침 검사가 틀립니다. 예약표에도 `90:0`처럼 찍힙니다. `old-bot.txt`를 따라가 보면 9:00~10:30 예약이 있는 대회의실에 9:30~10:00과 10:00~11:00 예약이 **둘 다** 들어갑니다. 같은 이유로 청소 시간 검사도 빠져나갈 수 있습니다.
- `"중회의실 A"`처럼 이름에 띄어쓰기가 있으면 번호로 바뀌지 않고 "없는 회의실"이 됩니다.
- 제목에 쉼표가 있으면 뒤가 잘립니다. 제목이 비어 있으면 원인 대신 "형식 오류"만 나옵니다. 운영 메모 6절의 안내와는 일치합니다.
- 인원을 비우거나 숫자가 아니면 0명으로 들어가 정원 검사를 늘 통과합니다(ROOM-19, 해결 안 함).
- 명령어 대소문자를 구분하지 않아서 `rsv`도 처리됩니다. 문서에는 언급이 없습니다.
- 예약이 500건을 넘으면 그 뒤 예약이 모두 "형식 오류"가 됩니다. 취소된 건도 500건에 포함됩니다. 운영 메모 3절에 적혀 있습니다.
- `RsvManager.java:11-13`의 배열 구조 주석은 상태 칸을 `[8]`이라고 하지만, 실제로는 `[7]` 인원, `[8]` 제목, `[9]` 상태입니다.
- QRY는 파일에서 **그 줄보다 앞에서** 처리된 예약만 보여 줍니다.
- 기획서에 있는 가예약(HLD)은 1차 범위에서 빠졌고, 코드에서도 "알 수 없는 명령"으로 처리됩니다. 이 부분은 문서와 일치합니다.

## 정리하면
문서가 여러 곳(README, 2010년 기획서, 총무팀 규정, 시설관리 문서, 운영 메모, 이슈)에 흩어져 있고, **README와 기획서가 가장 낡았습니다.** 지금 기준에 가장 가까운 것은 규정 댓글, 시설관리 문서, 운영 메모, 이슈입니다. 코드는 대체로 이 최신 결정을 따릅니다.

남은 차이는 성격이 둘로 나뉩니다.
- **문서만 고치면 되는 것**: 2시간→3시간, 청소 시간, 정원+2, DB 관련 설명 등
- **정책 결정이 필요한 것**: R06을 없앤 근거, ROOM-31 임원 판정, ROOM-12 변경 시 청소 시간, ROOM-23 세 자리 시각

앞으로 고칠 때는 두 번째 묶음부터 담당 부서와 확인한 뒤 손대는 것을 권합니다. 실제 실행으로 위 동작을 확인하려면 빌드와 실행 명령을 승인해 주세요. 결과물은 저장소 밖 `/tmp`에 만들도록 하겠습니다.
````

````markdown
## 실행 방법

```sh

- 다른 입력은 파일 이름만 바꾸면 돼요: `data/month.txt`, `data/old-bot.txt`, `data/empty.txt`.
- 결과가 지금 시각에 따라 달라지지 않아요. "2주 이내", "지난 시간" 같은 판단을 실행 시각이 아니라 각 줄의 요청시각으로 하기 때문이에요. 그래서 다시 돌려도 같은 결과가 나와요.

## 결과에서 README와 다른 점

코드는 고치지 않았어요. 결과를 보다가 README와 다르게 동작하는 곳이 보여서 적어 둘게요.

- **예약 길이 제한:** README는 "2시간까지"인데, 실제로는 3시간을 넘을 때만 막아요. 그래서 `[0021]` 14:00~17:00(3시간)이 통과했어요.
- **청소 시간:** README는 12:30~13:30인데, 오류 메시지는 `12:00~13:00`이라고 나와요.
````
